## 1. 目的とゴール

Taneのログインを有効にする前に、次の2つを済ませる。

1. 利用規約・プライバシーポリシーに、「Spraのほかのアプリ（Tane）とアカウントを共通にすること」と、その記録の扱いを書く。
2. すでに登録している人に、新しい版へ**同意しなおして**もらう。新しく登録する人は、登録のときに新しい版へ同意する（今のしくみのまま）。

ゴールは、`TANE_LOGIN_ENABLED=true` にした日から、**同意していない人のTaneの記録が、サーバーに預けられない**こと。

### 2-3. Tane側の規約・プライバシーポリシー

- 今のTaneの下書き（`company/spra/tane/docs/legal/`）は、「ログインがない・個人情報を集めない」前提。ログインを有効にするとき、**Tane専用の本文を持たず、Spra Goの規約・プライバシー（共通）へのリンクに置き換える**（共通アカウントの方針）。Taneに専用の条件が要る場合（計算の問題の正確さの免責など）だけ、短い補足をTane側に残す。【要確認】
- Tane側の変更は、別の依頼メモとして、Taneのチャットに渡す。

## 3. 版（バージョン）の扱い

- 版 = 制定日（`config/legal.php` の `version`、`docs/legal/terms.md` の「制定日」）。新しい版の日付は、**公開する日**（Ownerが決める）。
- **版を上げるのは、同意のしくみをデプロイして動作を確かめたあと、新しい本文の公開と同じ日**。先に版を上げると、本文が古いまま全員に同意を求めてしまう。
- 順番:
  1. 同意のしくみ（4章）をデプロイ（版は変えない → 誰にも画面は出ない）
  2. 専門家の確認ずみの本文を `docs/legal` に入れ、`sync-legal` で公開用に書き出し、版を上げてデプロイ → 既存ユーザーに画面が出る
  3. `TANE_LOGIN_ENABLED=true`・`TANE_LOGIN=on`（Taneの再ビルド）

## 4. 同意のしなおし（しくみ）

### 4-1. 「同意が古い」の判定
- `users.terms_version` が `config('legal.version')` と違う（空を含む）= 同意が古い。
- `GET /api/user` の返事に `terms_outdated: bool`（と現在の版 `terms_version_current`）を足す。

### 4-2. 同意する入口
- `POST /api/terms/accept`（`auth:sanctum`。クッキーでもトークンでも使える）入力 `{ version }`。`version` が現在の版と一致するときだけ受け付け（違えば 422。古い画面で別の版に同意させないため）。`terms_accepted_at = now()`、`terms_version = 現在の版` を記録 → 204。

### 4-3. Spra Go の画面
- ログイン後（`/profiles` の前を含む、ログインが必要な全画面の入り口）で、`terms_outdated` なら **同意の画面**（`/terms-update`）に送る。同意するまで先へ進めない。
- 画面の中身:
  - 「きまりが かわります」の見出し（子どもも見る画面なので、やさしい言葉＋保護者向けの説明）
  - 変わる点の要約（3行程度）: Tane とアカウントを共通で使うこと／どのアプリを使っているかを記録すること／記録はアプリごとに別々のこと／アカウントを消すと全部消えること
  - 全文へのリンク（`/terms`・`/privacy`。新しいタブ）
  - 「同意する」ボタン（保護者向け: 18歳以上の保護者が操作する旨）、「同意しない」（ログアウト。削除の申し出は問い合わせ窓口〔`info@spra.jp`〕へ、と案内）
- 同意の画面は、ログアウトと同意の操作以外を出さない。クッキーのログインは、これまでどおり同意の印がなくても**できる**（ログインを止めない。画面で止める）。

### 4-4. API で止めるところ
- **Tane の入口だけ**、同意が古い人は **403** `{ message, code: "terms_outdated" }`（`/api/tane/*` の記録と保護者の入口）。Taneの記録を預かる前に、必ず新しい版へ同意ずみにするため。
- Spra Go の既存の入口は止めない（これまでどおり。画面で止める）。
- トークンのログイン（`POST /api/auth/token`）は成功させ、返事の `user` に `terms_outdated` を含める。Tane の画面は、これを見て同意の画面を出す（5章）。

### 4-5. 新しい登録
- クッキーの登録・Googleの登録・Taneからの登録（`RegisterUser`）は、これまでどおり、現在の版を記録する。登録のチェック文（「利用規約とプライバシーポリシーに同意する」）に、「Tane など関連アプリでも同じ規約を使います」を足す（登録画面の1行）。

## 5. Tane 側（別の依頼メモにする）

- ログイン後、`user.terms_outdated` が true なら、Tane でも同意の画面を出す（要約＋Spra Go の規約・プライバシーへのリンク＋「同意する」→ `POST /api/terms/accept`）。Spra Go の画面へ誘導する案もあるが、Taneで完結するほうが離脱が少ない。
- 403 `terms_outdated` を受けたら、同じ画面へ。
- Tane専用の規約・プライバシーを、Spra Go の共通版へのリンクに置き換える（2-3）。

## 6. 削除の確認文
- プロフィール削除の確認文（`components/app/profile-sheet.tsx`）に「Taneの記録も消えます」を足す。`TANE_LOGIN_ENABLED` を on にするのと同時に出す（3章の順番の3）。
- 家族アカウントの削除は、いまは問い合わせ窓口で受け付ける（画面はない）。規約・同意の画面から案内する。画面を作るかは別の判断。

## 7. テスト

- `GET /api/user`: 版が違う／空 → `terms_outdated: true`、同じ → false。
- `POST /api/terms/accept`: 現在の版で204・記録が更新される／古い版・存在しない版は422／未ログインは401／トークンでも使える。
- `/api/tane/*`: 同意が古い人は403＋`code`、同意すると通る。`POST /api/auth/token` は成功し `terms_outdated` を返す。
- 登録（3経路）は現在の版を記録する（既存のテスト）。
- 画面: 同意が古いと `/terms-update` に送られ、同意すると元の画面に戻る。「同意しない」でログアウトする。
