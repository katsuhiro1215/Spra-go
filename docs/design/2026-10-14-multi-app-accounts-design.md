# Spra のアプリをまたぐアカウント — 設計書

- 作成日: 2026-10-14
- ステータス: **段階1は実装済み（2026-10-14）。段階2〜3はTaneの公開前に実装する**
- 前提: `company/spra/CLAUDE.md`（アカウント方針）、`company/spra/tane/docs/2026-10-14-game-foundation-design.md`（Taneの分割4）、`2026-10-13-ranking-design.md`（保護者のパスワード確認の考え方）

## 1. 目的

Spra Go・Tane・Spra World（開発前）を、**1つのアカウントで使えるようにし、どのアプリに登録・利用しているかを把握する**。

- Ownerが、管理画面で「Goだけ／Taneだけ／両方」を見分けられる
- 将来、複数のアプリを使っている人に、特典を付けられる（今は付けない。付けられる土台だけ作る）

## 2. Ownerが決めたこと（2026-10-14）

| 項目 | 決定 |
|---|---|
| Taneのログイン | **ログインなしでも遊べて、ログインすると記録が残る**（Spra Goと同じ） |
| アカウント | **共通のアカウントだけ**。Tane専用のアカウントは作らない |
| 把握したいこと | どのアプリに登録・利用しているか。Ownerの管理画面で見える |
| 特典 | 今は考えない。将来のために、把握だけできるようにする |

## 3. 守ること（既存の方針）

1. 共通にするのは**ユーザーまで**（ID・メール・パスワード）。子どものプロフィール・遊びの記録は、アプリごとに持つ。
2. 同じ人は**メールアドレス**で1人。Tane専用のアカウントを作れないので、2人に分かれない。
3. 子どもの情報を、アプリをまたいで勝手に混ぜない。Ownerが見るのは「どのアプリを使っているか」と、使い始めた日・最後に使った日だけ。
4. ログインなしの人は、記録に載らない（数えられるのは、登録した人だけ）。

## 4. データ

### 4-1. 新しい表 `user_apps`
| 列 | 中身 |
|---|---|
| `id` | |
| `user_id` | `users.id`（削除で一緒に消える） |
| `app` | `go` / `tane` / `world`（`config/apps.php` の一覧にあるものだけ） |
| `first_used_at` | そのアプリを初めて使った日時 |
| `last_used_at` | 最後に使った日時（日が変わったときだけ更新） |
| 一意制約 | `(user_id, app)` |

- 「登録したアプリ」は、**いちばん早い `first_used_at` の行**。専用の列は足さない。
- 既存の全ユーザーは、`go` の行を足す（`first_used_at` = 登録日、`last_used_at` = 登録日。マイグレーションで入れる）。
- 「使っている」の基準は、**ログインした状態で、そのアプリのAPIに触ったこと**。

### 4-2. アプリの一覧 `config/apps.php`
```php
'apps' => [
    'go' => ['name' => 'Spra Go'],
    'tane' => ['name' => 'Tane'],
    'world' => ['name' => 'Spra World'],
],
```
アプリを足すときは、ここに1行足すだけ。

## 5. 記録のしかた

- 画面（Spra Go・Tane）は、APIへのリクエストに **`X-Spra-App: go`（または `tane`）** のヘッダーを付ける。ネイティブアプリでも同じ（ブラウザの Origin に頼らない）。
- サーバーの小さなミドルウェア（`RecordAppUsage`）が、ログイン済みのリクエストで、次を行う。
  - ヘッダーが一覧にあるときだけ記録する。なければ何もしない（`go` に決め打ちもしない）。
  - `user_apps` に、なければ行を作る。あれば、`last_used_at` が**今日（日本時間）より前のときだけ**更新する（1日1回。リクエストごとに書かない）。
- ヘッダーは偽れるが、偽っても、自分のアカウントの印が変わるだけ。特典の判定に使うときは、「登録した」ではなく、**そのアプリで実際に何か記録がある**ことも合わせて確かめる（将来、特典を付けるときの設計で決める）。

## 6. Taneからのログイン（段階2）

### 6-1. 方式: アクセストークン（Sanctum のパーソナルアクセストークン）
- Spra Go は、いまのままクッキーのセッション（`go.spra.jp`）。**変えない**（本番のログインを巻き込まない）。
- Tane（`tane.spra.jp`）は、メールとパスワードで `POST /api/auth/token` を呼び、**トークン**を受け取る。以降は `Authorization: Bearer ...` で呼ぶ。
- 理由: クッキーを `.spra.jp` に広げると、WordPressの公式サイトにも届き、1つのサブドメインの不具合が全体に響く。トークンなら、ネイティブアプリ（React Native）でも同じ作りで使える。
- トークンは、有効期限つき（90日）・ログアウトで失効・端末名を記録・パスワード変更で全部失効。保存は、Taneの画面側（localStorage。XSS対策として、画面側の外部スクリプトを増やさない）。
- 試行の制限は、既存のログインと同じ（RateLimiter）。

### 6-2. 登録もTaneから
- Taneの画面から登録できる（同じ `users` に作る）。利用規約・プライバシーの同意チェックは、Spra Goと同じ（`terms_accepted_at`・`terms_version` を記録）。
- 登録したアプリは、Taneのリクエストで `user_apps` に `tane` の行ができて分かる。
- 登録直後に、家族アカウント（`user_schemas`）と最初のプロフィールを作る流れは、Spra Goの登録と同じ関数を使う（コピーしない）。

### 6-3. CORS
- `allowed_origins` に Tane の画面の場所（`TANE_URL`）を足す。トークンの道は `supports_credentials` が要らないが、既存と同じ設定のままでよい。

### 6-4. Googleだけで登録した人
- パスワードがないので、Taneのメール・パスワードのログインは使えない。
- 段階2では、**「パスワードを設定する」を案内する**（既存の設定画面にある）。TaneでのGoogleログインは、あとで足す（OAuthの戻り先の設計が要るため）。

## 7. Ownerの管理画面（段階1）

1. **ユーザー一覧**（`/owner/dashboard/users`）
   - 「アプリ」の列に、使っているアプリのバッジ（Go・Tane・World）。
   - 絞り込み: すべて／Goだけ／Taneだけ／複数（2つ以上）。
   - 各行に、アプリごとの使い始めた日・最後に使った日（ホバーまたは展開）。
2. **ダッシュボードの要約**に、アプリ別の人数と「複数のアプリを使っている人」の数を足す。
3. CSVの書き出し（既存の `export/users` があれば）に、`apps`（`go|tane`）の列を足す。
4. `/api/owner/users` の返事に、`apps: [{app, first_used_at, last_used_at}]` を足す。Taneの行は、段階2まで、まだ出ない。

## 8. 特典の土台（今は作らない）

- 「複数のアプリを使っている人」は、`user_apps` を `user_id` で数えるだけで出せる。
- 特典を付けるときの考え方（あとで設計）:
  - 付ける先は、ユーザー（家族アカウント）。コインを足すなら、どのプロフィールに足すかを決める。
  - 同じ特典を二重に付けないよう、`user_benefits`（ユーザー・特典名・付けた日）の表で記録する。
  - 子どもの情報を見て判定しない。判定に使うのは、アプリの利用の有無だけ。

## 9. 法務（段階3。Taneの公開前に必須）

プライバシーポリシーと利用規約に、次を足す（`docs/legal/`、専門家の確認を受ける）。

1. 「Spra」のほかのアプリ（Tane・Spra World）と、**アカウントを共通にする**こと。
2. 「どのアプリを使っているか」と、使い始めた日・最後に使った日を記録すること、そして、**お知らせや特典のために使う**こと。
3. 子どもの学習の記録は、アプリごとに別々に保存し、アプリをまたいで見せないこと。
4. アカウントを削除したときは、すべてのアプリの記録が消えること。
5. 利用規約の「本サービス」の範囲に、Taneなどを含めること。

**同意のしなおし**: 利用目的が変わるので、版（`config/legal.php` の `terms_version`）を上げ、**すでに登録している人には、ログイン後に、新しい版の確認の画面を出す**（同意するまで先へ進めない）。いまは「同意の印がなくてもログインできる」仕組みなので、版が古い人にだけ確認の画面を出す機能を、段階3で作る。

### 10-1. Taneの公開（2026-10-28ごろ）は、ログインなし（Owner決定 2026-10-14、案A）

- Taneは、ログインなし・端末の中だけに記録して公開する。ログインは、公開の1〜2週間後に足す。
- 公開の時点でTaneに要るのは、**Taneの短い利用規約とプライバシーポリシー**だけ（個人情報を集めないことを書く）。下書きは `company/spra/tane/docs/legal/`。
- 共通アカウントの法務（9章）と、同意のしなおしは、ログインを足すときにまとめて行う。
- 日程の目安: 公開（10/28）→ 段階2・3（トークンのログイン・規約の版の更新・同意のしなおし）を、11月上旬までに、Tane公開後の様子を見ながら。
- 段階1（記録）は先に出ているので、ログインを足した日から、Taneの利用が `user_apps` に残る。

## 11. テスト

- 段階1:
  - ヘッダー付きのログイン済みリクエストで、`user_apps` に行ができる。同じ日の2回目は更新しない。日が変わると `last_used_at` だけ更新される。
  - 一覧にないアプリ名・ヘッダーなし・未ログインでは、記録されない。
  - 既存ユーザーが、マイグレーション後に `go` の行を持つ。
  - `/api/owner/users` に `apps` が付く。複数の絞り込みの結果が正しい。
  - Owner以外は、`apps` の情報を見られない。
- 段階2: トークンの発行・失効・期限・試行の制限、Taneからの登録で同意が記録される、Googleだけの人の案内。
- 段階3: 版が古い人にだけ、確認の画面が出る。同意すると、版と日時が更新される。

## 12. リスクと、決めておくこと

| 事項 | 内容 |
|---|---|
| APIの場所 | いまは `api.go.spra.jp`。Taneが使うと名前が合わない。**いまは変えない**（段階2のあとで、`api.spra.jp` を足すか検討。足すだけで、古い場所は残せる） |
| 1か所に集中 | Taneのログインは、Spra Goのサーバーに頼る。止まると、Taneの「ログインして記録を残す」だけが止まる（ログインなしの遊びは、止まらない） |
| 子どものプロフィール | Taneは、Spra Goと同じプロフィール（名前・アバター）を共通で使う方針。**Tane側の遊びの記録は、プロフィールIDにひもづけて、Taneの表に持つ**（Spra Goの記録とは混ぜない）。Taneの設計書で決める |
| アカウント削除 | すべてのアプリの記録が消える。段階2で、削除の確認画面に「Tane・Spra Worldの記録も消えます」と出す |
| 偽のヘッダー | 3章・5章のとおり、特典の判定には使わない |
| 法務 | 9章の文は、専門家の確認を受ける。同意のしなおしは、一部の人が離れる可能性がある |
